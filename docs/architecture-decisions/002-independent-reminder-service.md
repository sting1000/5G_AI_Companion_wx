# 决策：参考 K12 模式新建独立提醒服务

## 背景与问题

现有 K12 项目有 FastAPI、PostgreSQL、鉴权和模型调用经验，但其用户、数据、配额和发布流程属于教育问答领域。老人提醒需要独立演进和部署。

## 候选方案

- A：直接在 K12 后端增加提醒路由和数据表——启动快，但会耦合性能、数据、迁移和发布风险。
- B：参考 K12 的工程模式，在单独服务器新建最小服务——需要独立初始化，但故障和数据边界清楚。
- C：不建服务，全部保存在手机——最简单，但无法支持云同步、子女角色和未来运营商集成。

## 决策

选择 B。新服务可借鉴 K12 的 FastAPI 分层、配置管理、超时重试、PostgreSQL迁移和健康检查，但不运行时依赖 K12，也不修改 K12 数据库。

## 为什么（用户复述）

“有一台单独的服务器可以用；复用会影响 K12 的性能，以及数据混乱。”

补充：独立服务还能避免老人提醒的故障、凭证和发布节奏影响 K12 的真实用户。

## 可迁移原理

可复用的是经过验证的工程模式；当领域、身份和发布节奏不同，默认隔离服务与数据，而不是复用生产运行时。
